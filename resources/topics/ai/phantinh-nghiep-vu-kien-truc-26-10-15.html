01

Sản phẩm là gì

Một app phản tỉnh và tư duy hệ thống cho một người, dùng Claude Code làm bộ não thay cho API key.

README tự mô tả: “A personal reflection & systems-thinking app. Each chat session is bound 1:1 to a real Claude Code TUI session running in tmux on your host; the PWA is the structured front end, your terminal is the live observer.”

Yêu cầu gốc (phantinh-requirement.md) đặt ra vài ràng buộc định hình toàn bộ kiến trúc:

  • Không có API key. Mọi lượt AI phải chạy qua Claude Code CLI đã đăng nhập sẵn trên máy. Web chỉ là lớp vỏ có cấu trúc đứng trước terminal.
  • Không đăng nhập. Bỏ qua login, vào thẳng dashboard. Không có bảng user; các bảng hồ sơ học tập gắn 1–1 với Module.
  • Mọi thứ lưu trong DB. Mỗi luồng nghiệp vụ bắt đầu từ một câu hỏi hoặc nỗi đau và kết thúc bằng một báo cáo.
  • Cài được như PWA, gọi bằng phím tắt (về sau là Raycast).

Khi subscribe, nếu phiên đóng vì idle và tmux còn, dòng quay về ACTIVE và tailer chạy lại.

B3 · Gặt cứng

Giết phiên tmux không có dòng DB, đóng vì timeout, hoặc đã đóng quá 1440 phút.

Sức khỏe. /livez chỉ kiểm DB và Redis, là healthcheck của container api mà ba container vòng lặp chờ, nên chúng khởi động được cả khi shim trên host chưa chạy. /healthz thêm bridge doctor, dùng để quan sát (make healthz). Compose kiểm pg_isready và redis-cli ping cho db, redis.

Tài khoản. Claude Code lưu grant OAuth theo từng CLAUDE_CONFIG_DIR trong keychain macOS. Bridge đọc trạng thái mà không làm mới token, đồng bộ grant giữa các thư mục, và chạy đăng nhập trong một phiên tmux riêng rồi mở URL đúng hồ sơ trình duyệt. Trước mỗi spawn, một bước kiểm chặn phiên mới nếu grant đã hết hạn.

Test. Bats cho bridge (make test-bridge): doctor, mọi lệnh con, tách JSONL, profile oneshot, tài khoản, ebook, akm, và đối chiếu danh sách kind. Pytest cho API trong container.

01

What the product is

A reflection and systems-thinking app for one person, using Claude Code as its brain instead of an API key.

The README describes itself: “A personal reflection & systems-thinking app. Each chat session is bound 1:1 to a real Claude Code TUI session running in tmux on your host; the PWA is the structured front end, your terminal is the live observer.”

The original requirements (phantinh-requirement.md) set a few constraints that shape the whole architecture:

  • No API key. Every AI turn must run through the Claude Code CLI that is already logged in on the machine. The web is a structured shell in front of the terminal.
  • No login. Skip sign-in and go straight to the dashboard. There is no user table; learning profiles are one-to-one with a Module.
  • Everything is stored in the DB. Each business flow starts from a question or pain point and ends in a report.
  • Installable as a PWA, opened with a hotkey (later, Raycast).

09

The TUI chat flow

A message goes out by pasting into tmux; the reply comes back by reading the JSONL transcript Claude writes itself.

  1. 1createSessionBuild the opening (static, or a template + profile), create a PROVISIONING row
  2. 2bridge spawntmux new-session, wait for the TUI's session UUID (up to 15 s), paste the opening, find the JSONL file
  3. 3ACTIVEStore the tmux name, session id, JSONL path, attach command; start the tailer
  4. 4sendMessageA USER row, then bridge send pastes into the pane + Enter
  5. 5tailEach JSONL line becomes an event: turn_started, turn_event (text, tool_use, tool_result, thinking), turn_complete
  6. 6tailerPublish to Redis, write Message, Report (if there is a YAML report block), TurnLatency; only then advance the cursor
  7. 7sessionStreamThe subscription reads Redis pub/sub and pushes 4 chunk types over graphql-ws
C1Invariant

The cursor advances only after the writes land

Rule

jsonl_cursor moves only after side effects succeed, and only forward.

Example

The API reloads mid-turn 7. The next subscribe sees an ACTIVE row with no tailer, calls ensure_tailer, and reads again from the stored cursor. Every write is idempotent, so no message is duplicated.

C2Invariant

Tools that block on a human are disabled

Rule

Every TUI session runs with --disallowedTools "AskUserQuestion ExitPlanMode".

Example

If Claude asked through AskUserQuestion, that turn would end in tool_use, not end_turn, and would not reach the JSONL until someone answered in the TUI. The web would show your message with no reply, and the session would sit ACTIVE forever.

C3Design

The report travels inside the reply

Rule

The skill prints a ```yaml block marked ---phan-tinh-report---. The bridge lifts it out as report_block; the API checks it against report_schema and renders markdown.

Value

A free-form chat still ends in a structured report you can store and print.

The one-shot flow

One prompt in, one schema-valid JSON out. Every door (web form, lenses, follow-ups, business reports, Raycast) goes through one engine.

  1. 1prepare(RunSpec)Check kind, mode, inputs against the schema, provider, profile — before any row exists
  2. 2create_rowA PROVISIONING row with the full lineage; hold a Redis lease
  3. 3runWait on the shared semaphore (3 at a time), build the prompt with $-substitution
  4. 4bridge oneshotclaude -p --json-schema … --output-format json, prompt on stdin
  5. 5StoreRe-check the payload, render markdown, write Report + run_meta, extract learning points, CLOSED
  6. 6Follow-upOptional: start a child run, at most 3 levels

oneshot/engine.py is the only place a one-shot run is created, executed, failed or retried; a test guards that boundary.

Each outer layer waits longer than the inner one, so the error always comes from the layer that knows the cause best.

C4Invariant

A lease for a reaper in another container

Rule

Redis key phantinh.oneshot.lease.<id>, TTL 180 s, refreshed every 60 s. The reaper closes a PROVISIONING row only once its lease has expired.

Example

A research run takes 8 minutes. The reaper runs every 10 minutes and sees a PROVISIONING row older than 5 minutes, but the lease is alive, so it skips it. If Redis does not answer, the reaper skips every one-shot row that tick.

C5Tested

The render contract

Rule

Every field substituted into a template must be required in the schema; modules without modes may substitute only scalar values.

Example

safe_substitute leaves $name in place when a field is missing, and prints a list as a Python repr. The test found 33 violations, all fixed; the fix is a pre-rendered “twin” field such as corrections_markdown.

host-shim.py

A standard-library HTTP server with 3 endpoints: POST /run runs one bridge command, POST /tail streams chunked NDJSON, GET /health. A POST must be application/json (so a foreign web page is stopped at the preflight) and carry a local Host, or a Bearer PT_HOST_SHIM_TOKEN when one is set; without a token it refuses to bind anything but loopback. The token is not passed down to the bridge. It writes a pidfile; the readiness probe compares the serving pid with the pidfile to catch a stale shim holding the port.

One shared event contract

shared/protocol defines the Pydantic event union and the Redis channel name for both the bridge and the API. The Python RunProfile must match _profiles.sh; a bats test checks it.

C6Tested

Private values never leave the browser

Rule

A mask rule must behave the same in JS and Python (JS syntax, ASCII semantics, no empty matches). If the stored rule set no longer parses, the router turns OFF rather than letting a question through unchecked.

Example

With \b around numbers, _ counts as a word character, so <PHONE_0901234567> would smuggle a raw phone number past the check. That is why the rules use digit lookarounds and token indexes are capped at 4 digits.

C7Measured

Rule

manage.py eval_site_router runs 20 real questions through the same code as the mutation, with no DB writes; 5 are held out and never used to tune hints. eval_assistant does the same for UzAI inside lessons.

On 2026-10-16: 20/20 hits, 5/5 on the held-out set, and the first link was right 18/20 times.

Operations: sessions, cleanup, accounts

Who moves a session's state, and how the system heals itself.

B1 · Soft close

ACTIVE idle over 60 minutes → idle_ttl. PROVISIONING over 5 minutes with no lease → provisioning_timeout. tmux and Claude stay alive.

B2 · Revive

On subscribe, if a session closed for idleness and its tmux is alive, the row goes back to ACTIVE and the tailer restarts.

B3 · Hard reap

Kill tmux sessions that have no DB row, closed on timeout, or closed more than 1440 minutes ago.

Health. /livez checks only the DB and Redis. It is the api container's healthcheck, which the three loop containers wait on, so they start even while the shim on the host is down. /healthz adds bridge doctor and is for monitoring (make healthz). Compose checks pg_isready and redis-cli ping for db and redis.

Accounts. Claude Code stores its OAuth grant per CLAUDE_CONFIG_DIR in the macOS keychain. The bridge reads the status without refreshing the token, syncs grants between directories, and runs sign-in in its own tmux session, opening the URL in the right browser profile. Before every spawn, a pre-flight check blocks a new session if the grant has expired.

Tests. Bats for the bridge (make test-bridge): doctor, every subcommand, JSONL parsing, one-shot profiles, accounts, ebook, akm, and the kind-list comparison. Pytest for the API inside the container.

Admin: settings and troubleshooting

Each setting starts in a file, is edited in one tab, and is read back by one part of the code. The operating pages use the same data to find faults.

A session's quality score. /admin/sessions scores each session green, amber or red. Red when the session is in ERROR, a turn has been stuck mid-stream for over 5 minutes, the report failed schema validation, or the JSONL transcript has more turns than the DB (sync drift). Amber for any other issue: bridge errors, closed with no report, average TTFT over 30 s, a very short session.

Design principles

Invariants read from the code and plans, each held by a test or a docstring.

  1. The DB is authoritative; YAML is only a seed. Config is read per request from the Module row and degrades to named defaults instead of raising, so a half-edited config never makes a page return 500.
  2. The host does what the container cannot. tmux, git worktrees, book files, PDFs, say and AKM transcripts all go through the bridge.
  3. One protocol, defined once in shared/protocol, shared by the bridge and the API.
  4. Ingestion can always resume. The cursor advances only after writes land; every write is idempotent.
  5. Redis holds live state, Postgres holds durable state.
  6. One door into one-shot runs, one concurrency cap. Retries keep the lineage; a refused run becomes a re-runnable ERROR row.
  7. Pure cores, thin resolvers. reasoning, training, decision, canonical, paragraph, ebook and mustwin never touch the ORM and are unit-tested.
  8. Check structure; don't copy the parsers' rules.
  9. Security lives in code. CLI permissions come from profiles, extra args pass an allowlist; the shim requires a local Host or a token; private values are masked before they reach the model; the must-win guard code is checked in the API, fails closed and covers respawn; the runtime snapshot never stores env; UzAI's tool scope is enforced by code.
  10. History is append-only.
